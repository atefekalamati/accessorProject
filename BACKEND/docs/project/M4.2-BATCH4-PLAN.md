# M4.2 batch 4 — plan ADM-02 و ADM-08 (2026-10-26)

هر دو HIGH هستند و بازبین opus دارند: ADM-02 به خاطر وضعیت سفارش و صدازدن release موجود، و ADM-08 به خاطر پول و بازپرداخت (دستور کاربر). هیچ‌کدام سرویس reserve/commit/release را تغییر نمی‌دهند، پس طبق AUTOPILOT متوقف نمی‌شوند. مرجع: «مدیریت سفارش» ✓، ADR-047، ADR-048، ADR-050، ADR-051 و ADR-053 (D35).

## ADM-02 — وضعیت ارسال، کد رهگیری و لغو ادمین (4h)

**migration `20261026_0026_create_shipments`:**
- جدول `shipments`. ستون‌ها:
  - `id`
  - `order_id`: FK به orders با RESTRICT، UNIQUE (رابطه 1:1)
  - `tracking_code`: VARCHAR(64)، nullable، CHECK trim و ناتهی
  - `shipped_at` و `delivered_at`: هر دو DateTime(tz)
  - timestamps
- CHECKها: `delivered_at` ⇒ `shipped_at`، `shipped_at` ⇒ `tracking_code`، و `delivered_at ≥ shipped_at`.
- مدل در `app/db/models/orders.py`؛ ثبت در `__init__`، `_MODELS` و `EXPECTED_TABLES`.

**`PATCH /admin/orders/{id}/shipment`:**
- مجوز `orders:update_status`. ترتیب: اول authorization، بعد بدنه.
- بدنه با `extra=forbid`: `{status: preparing|shipped|delivered, tracking_code?}`.
  - `tracking_code` فقط و الزاماً با `shipped` می‌آید (۱ تا ۶۴ کاراکتر چاپی، trim). در غیر این حالت 400.
- تراکنش:
  1. بررسی وجود سفارش بدون lock (404).
  2. `order_advisory_lock` → `lock_order` (ADR-048؛ قفل سبد لازم نیست، چون سبد و موجودی دست نمی‌خورند).
  3. `check_transition` → 422 `INVALID_STATE_TRANSITION`. همان وضعیت → 422 `same_status`؛ PATCH idempotent نیست، مثل state machine.
  4. `OrderStateService.transition` روی shipment، که history و audit `order.status_changed` با actor ادمین می‌سازد.
  5. ردیف `shipments`: در `preparing` ساخته می‌شود؛ در `shipped`، `tracking_code` و `shipped_at` ثبت می‌شود؛ در `delivered`، `delivered_at` ثبت می‌شود و در همان تراکنش transition `order → completed` انجام می‌شود (guard `requires_shipment_delivered`).
  6. audit `shipment.updated` با `tracking_code` (PII نیست).
- `now` بعد از lockها گرفته می‌شود.
- پاسخ: همان جزئیات ادمین ADM-01، به‌علاوه `shipment` (`no-store`).

**`POST /admin/orders/{id}/cancel`:**
- مجوز `orders:update_status`. همان مسیر لغو مشتری (`OrderService.cancel`)، بدون فیلتر کاربر.
- `OrderCancellation.cancel_locked` پارامتر جدید `reason: CancelReason = CUSTOMER` می‌گیرد. ادمین `ADMIN` را پاس می‌دهد. انقضا همچنان بر `expired` اولویت دارد.
- payment `pending` → 409 `PAYMENT_IN_PROGRESS`. سفارش لغوشده → 200 بدون نوشتن. سفارش پرداخت‌شده یا confirmed → 422 (guard موجود `already_paid` / `not_allowed`).
- رزرو با `release()` موجود و redemption با `RedemptionService.release` آزاد می‌شوند، با ترتیب lock موجود.

**`GET /orders/{number}` (ACC-01) و جزئیات ادمین:** `shipment` از جدول خوانده می‌شود (تا امروز null بود).

**تست‌ها:**
- مسیر کامل روی سفارش paid: `preparing → shipped` (بدون کد → 400) `→ delivered` و order `completed`. history و audit با actor ادمین.
- انتقال نامعتبر → 422: preparing روی سفارش unpaid، پرش `not_shipped → shipped`، همان وضعیت.
- مجوزها: support فقط `orders:read` دارد → 403؛ content_manager → 403.
- لغو ادمین: unpaid → `cancelled/admin`، رزرو released و redemption released. pending → 409. paid → 422. تکرار → 200.
- همزمانی:
  - دو PATCH `shipped` همزمان → یکی 200 و یکی 422.
  - لغو ادمین ∥ callback موفق → یا `cancelled` + `refund_required`، یا `paid` + لغو 422؛ هرگز هر دو.
  - لغو ادمین ∥ لغو مشتری → یک اثر.
- `GET /orders/{number}` مشتری `shipment` را نشان می‌دهد.

**ریسک‌ها:** deadlock (فقط advisory → ردیف سفارش → مسیرهای موجود)؛ لغو سفارش paid (guard موجود + تست)؛ کامل‌شدن بدون تحویل (guard + تست).
**rollback:** `git revert`؛ downgrade migration فقط جدول `shipments` را حذف می‌کند.

## ADM-08 — ثبت بازپرداخت دستی (3h، D35)

**migration `20261026_0027_add_payment_refunds`:**
- `refunded` به CHECK وضعیت payments و `orders.payment_status` اضافه می‌شود.
- ستون‌های payments:
  - `refund_reference`: VARCHAR(100)، unique partial `WHERE NOT NULL`
  - `refunded_at`: DateTime(tz)
  - `refunded_by`: FK users با RESTRICT؛ کاربر فقط حذف نرم می‌شود
- CHECKها:
  - `(status = 'refunded') = (refund_reference IS NOT NULL AND refunded_at IS NOT NULL)`
  - CHECK `failure_reason` شامل `refunded` شود: refunded دلیل refund_required را نگه می‌دارد (amount_mismatch، duplicate_payment، late).
  - `paid_at` در CHECKهای paid و refund_required به `refunded` هم تعمیم یابد.
- downgrade: اگر ردیف refunded وجود داشته باشد متوقف می‌شود (بدون حذف داده).

**state و enum:**
- `PaymentStatus.REFUNDED`.
- جدول ردیف payment: `refund_required → refunded`.
- جدول order payment (ADR-047): `refund_required → refunded`.

**بستن no-opها (حیاتی):**
- `processing._decide`: payment `refunded` → `ALREADY_PROCESSED`. callback یا verify دیرهنگام بعد از بازپرداخت هرگز چیزی را عوض نمی‌کند.
- reconciliation و init فقط `pending` را می‌بینند؛ با تست تأیید می‌شود.

**`POST /admin/payments/{id}/refund {refund_reference, note?}`:**
- مجوز جدید `payments:refund` (seed؛ admin و super_admin). بدنه با `extra=forbid`. `note` تا ۵۰۰ کاراکتر و فقط در audit ذخیره می‌شود. مبلغ در بدنه نیست، چون فقط بازپرداخت کامل داریم.
- ترتیب lock: payment بدون lock (404) → `order_advisory_lock(order)` → `lock_order` → ردیف payment `FOR UPDATE` (ADR-048؛ همان ترتیب callback).
- قواعد:
  - `refunded` با همان reference → 200 بدون نوشتن (idempotent).
  - `refunded` با reference دیگر → 409 `CONFLICT` (`already_refunded`).
  - وضعیت غیر `refund_required` → 422 `INVALID_STATE_TRANSITION`.
  - reference روی payment دیگر → 409 (پیش‌بررسی، و `IntegrityError` با نام index → 409).
- اثر:
  - payment → `refunded`، با `refund_reference`، `refunded_at` و `refunded_by`؛ `failure_reason` و `paid_amount` می‌مانند.
  - order payment `refund_required → refunded`، فقط اگر هیچ payment دیگری از همان سفارش هنوز `refund_required` نباشد. وگرنه فقط ردیف عوض می‌شود. پرداخت دوم روی سفارش paid هم order را عوض نمی‌کند (`check_transition`).
  - audit `payment.refunded` با مبلغ `paid_amount`، reference و note (actor ادمین). log INFO بدون PII.
- «فروش موفق» تغییر نمی‌کند (`refunded ≠ paid`).

**تست‌ها:**
- مسیر کامل: انقضا → callback موفق → refund_required → refund → refunded. history و audit.
- تکرار با همان reference → 200 بدون audit دوم. reference دیگر → 409. reference تکراری روی payment دیگر → 409.
- refund روی paid، pending یا failed → 422.
- duplicate روی سفارش paid → فقط ردیف refunded؛ order paid می‌ماند.
- دو payment refund_required روی یک سفارش لغوشده: اولی order را refunded نمی‌کند، دومی می‌کند.
- callback و reconcile بعد از refunded → `already_processed` بدون تغییر.
- همزمانی:
  - دو refund با یک reference → یک نوشتن.
  - دو reference متفاوت → یکی 200 و یکی 409.
  - refund ∥ callback همان payment → سریال، بدون deadlock.
- مجوز: support → 403. فیلتر `GET /admin/payments?status=refunded`.

**ریسک‌ها:**
- ثبت دوباره بازپرداخت: unique و idempotency.
- پاک‌شدن دلیل یا مبلغ: CHECK و تست.
- callback دیرهنگام که بازپرداخت را لغو کند: no-op و تست.
- deadlock: ترتیب ADR-048 و تست.

**rollback:** `git revert`. downgrade فقط بدون ردیف refunded اجرا می‌شود.
